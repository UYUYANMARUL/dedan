## Decisions already taken

| Decision | Choice |
|---|---|
| Language | Rust for every service (one Cargo workspace), Solidity for contracts |
| Node engine | Pingora 0.9 with `pingora-cache` (in memory today; a Dedan-written disk storage is M4) and the rustls TLS backend (per-SNI certificates swapped without restart) |
| TLS | Per-node keys and certificates; control plane runs ACME under Dedan's account; Let's Encrypt `shortlived` profile, `default` as the degraded-mode switch |
| Chain | World Chain (World ID 4.0 verifier on-chain, native USDC, cent-level gas); Dedan's own ENSv2 tree on it (root → `eth` → `dedan`), bridged to canonical L1 `dedan.eth` when ENSv2 reaches mainnet; contracts immutable with governance-settable parameters |
| Economics | Slot-based pay × audited quality (ARCHITECTURE §6, §8) |
| Steering | Crowd-sourced latency map keyed by H3 resolution-2 cell (about 300 km), kept by `DedanCells` on chain: nodes join cells, `ROLE_ATTESTER` holders attest a cell's members at most once a minute per cell, one vote per human per node per cell (newest sample), per-day histograms of 8 ms buckets, median over today and yesterday as the `dedan.latency` record of `<label>.<cell>.dedan.eth`; resolvers mirror it from the events (`core::map::from_votes`) |
| Identity | ENSv2: a node is `<label>.dedan.eth`, a token in `DedanRegistry`; its endpoint and config are the name's records (`addr(60)`, `dedan.*` text, DNS A/AAAA); cells are `<h3 hex>.dedan.eth` with `DedanRegistry` as their subregistry, so `<label>.<cell>.dedan.eth` is the node inside a cell (same token, records keyed by the full namehash); every permission is an Enhanced Access Control role: World ID proofs grant `ROLE_NODE_OPERATOR`, `ROLE_ATTESTER`, `ROLE_AUDITOR` on a per-human resource, owners grant `ROLE_NODE_SIGNER` on their name, governance holds the root roles; no CCIP-Read, one chain |
| Auditors | One app, two record types: location-tagged attestations for the map, assigned probes with tokens for quality and class |
| Scope for v1 | classes 100M/1G (1G only when auditors can prove it), node counts 3/6/12, no pinned tier, no metered billing, no web UI, no HTTP/3, no DNSSEC, resolver operators permissioned, k = 2 countersigning, no automatic slashing |
| Build order | Identity (contracts, core, nameserver) first because every service reads it; then the settlement loop (auditor + aggregator); then the traffic path (node, control plane) |
| Mocks | Live only under `deploy/`, stand in only for things outside the codebase (chain, CA, World ID for the scripted humans, USDC, customer DNS, origin) or for services not yet built. Every crate is the real implementation; the only devnet-specific behaviour in a crate is a flag that shortens a period, lowers k, or points at a local endpoint |

**Simulated WAN.** `deploy/wan/hosts.txt` (name, city, ip, role, lat, lon) is the one source: 10.77.0.0/16, one /20 per city (`10.77.<16c>.0/20`), each node its own /24 inside it, origin and users inside their city's /20; `wan.sh` sets one `tc netem` band per city from `latency.txt`. Measured 2026-09-26 from Istanbul: CSS hit 10 ms local, 99 ms Frankfurt, 283 ms New York, 572 ms Tokyo.

**Customer DNS onboarding.** `deploy/resolver/zones/images.com.zone` holds `www CNAME acme.dedan-cdn.test` and `_acme-challenge.www CNAME _acme-challenge.acme.dedan-cdn.test`. The nameserver serves that zone as the customer's DNS provider and chases the CNAME into its own zone. `acme` answers from the account's slot set (`core::assign` over the ENS node table), ordered for the client's cell (ECS or source IP → `hosts.txt` on the devnet) by the map built from the chain's `Attested` and `KeyRevealed` events (`core::map`, k = 1 on the devnet), and by distance to the nodes' declared locations while the map has nothing for that cell. `make demo` has each city's attester ping every node and send one `attest` batch with the tokens the nodes minted, then shows `dig +subnet` per city answering from the chain, and a spoofed batch from Istanbul claiming the Tokyo cell landing in `/map` evidence because its /24 is Istanbul's.

**Devnet growth.** Done: the /16 layout above, five users, one netem band per city, and node cities added at runtime through `add-node.sh` (up to five) and clients through `add-client.sh` (up to fifteen); `wan.sh` has fifteen delay bands. The origin serves five PNG photos under `/images/` besides the blobs; `routing-check.sh` fetches one of them from every city's user, static and added.

**Devnet inputs that replace unbuilt services.** Until M3: `deploy/devnet/nodes.json` (label, ip, port, class, location, cell, operator/hotKey/attester key index, user container), `deploy/devnet/accounts.json` (label, hostnames, node count, class, availability), `deploy/devnet/keys.json` (the static hourly key the mock nodes mint with and reveal on chain). What the mocks replace: `MockUSDC` for USDC; `MockWorldID` (any proof with a non-zero nullifier) for the World ID verifier; the zone files for the customers' DNS providers; Pebble for the CA; nginx for the nodes; `StubGatewayProvider` (no gateways) for the Universal Resolver's CCIP-Read. The smoke: stage 1 registers an operator (World ID mock) and the node `smoke.dedan.eth` with a hot key and records, an attester attests, an auditor stakes, the hot key reveals a token key, the Universal Resolver resolves `dedan.class`, the operator rewrites the node's A record and nobody else can; then one settlement day (roots, +73 h, stage 2 claims); lego certificate for `www.images.com` + `istanbul.node.dedan-cdn.test` through the nameserver's TXT API; origin fetch.

### M0 — Contracts and devnet: done
Before testnet: point the registry at the Sepolia verifier (`setWorldId`), set `rpId` to the app's, turn the gate's fallback off, choose the governance multisig and timelock.

### World ID (real IDKit): built
WORLD-ID.md has the trust moment, the credential choice, the flow, the paths without a role, running it and the integration debrief. The dashboard's World ID section runs IDKit 4 in the browser (`@worldcoin/idkit-core` 4.3.0, Proof of Human only, the account as the signal, a QR for World App or a link for the simulator); the control plane is the relying party (`/v1/world-id/config`, `/request` signs with the RP key, `/verify` checks version, action, environment, credential, signal and its own nonce, then the Developer Portal's `/api/v4/verify`, then the nullifier on chain) and attests the proof for `WorldIdGate`, which the registry calls on the devnet; `MockWorldID` stays only as the gate's fallback for the scripted humans. Notes from building the crate: envelopes sign `keccak256(signer ‖ 0x00 ‖ ts ‖ nonce ‖ canonical JSON)` in the EIP-191 form through alloy's local signer, so no separate `k256` dependency; the fetch token MAC is `HMAC-SHA256(k_hour, "<minute>|<client /24>")` in hex (IPv6 /48) (test vectors from Python's `hmac`, the nginx mock must produce the same string); the Merkle tree reproduces `@openzeppelin/merkle-tree`'s layout, checked against roots computed with `cast`; the SLA credit test uses the Wilson *upper* bound (a shortfall must be significant), which corrected a wording error in ARCHITECTURE §8; `Map` and `Assignment` are the same code the resolver, aggregator and `recompute` will call.

### M2 — Settlement loop on the mocks (`make demo-settlement`): done (Sep 26, 2026)
- Auditor (`crates/auditor`, `dedan-auditor`): one process per human. At start it grants itself `ROLE_ATTESTER` (World ID proof) and `ROLE_AUDITOR` (proof plus the minimum stake, approved and pulled from its USDC) if it lacks them. Every `DEDAN_SYNC_SECS` it replays the registry and the cells contract, reads the names' records through the Universal Resolver, takes the account-signed configs the control plane relays (each verified against the account key on chain), rebuilds the map and the assignment with `dedan-core` (sticky on the aggregator's published period) and samples each account's asset list with the day's seed (`core::schedule`). From its `DEDAN_LOCATION` cell it measures the cell's members (the shortest of three TCP connects, two fetches with the customer hostname for the token and the cache-hit TTFB) and sends one `attest(cell, batch)` to `DedanCells` at most once a minute; the network it reports is the one inside the node's token. For each account the schedule assigned to it (`schedule::auditors_for`) it runs the schedule's slots (`core::schedule::slot`: landing probes through its own resolver alternating with targeted probes to each member in turn, exponential waits with mean `DEDAN_PROBE_MEAN_SECS`), records status, TTFB, cache-hit TTFB, TCP RTT, decoded sha256, bytes, Mbps and the node's token, and ships signed `ProbeBatch` envelopes every `DEDAN_BATCH_SECS`, keeping them for the next try when the aggregator's receipt is missing or not its. `DEDAN_DEVNET_LIE=1` fabricates every result and token; `DEDAN_PROBES=0` attests only.
- Aggregator (`crates/aggregator`, `dedan-aggregator serve`): `POST /v1/probe-results` verifies the envelope against the identity cache (clock window, `auditor:<addr>` holding the role and the stake, replay) and appends it to `data/inbox/<wall period>.jsonl`, answering a receipt signed by the aggregator key. At every period close (`DEDAN_PERIOD_SECS` + `DEDAN_GRACE_SECS`) it writes `inputs/` (below) for contract period `lastPeriod + 1`, runs `settle::compute` (identity folded from the events, envelope verification, tokens against the reveals, map, assignment sticky on the previous outputs, `core::score`, leaves with proofs, the digest the contract signs), writes `outputs/`, signs, asks the countersigner and calls `publishRoot`. A voided period stops the loop (a void is a dispute): an operator republishes it with `publish DIR` once the dispute is settled, and no later period is accepted before. `GET /v1/previous` serves the latest published period's sets, member quality and cumulative bills to the resolvers and auditors. `GET /periods` lists what it published.
- Countersigner (`dedan-aggregator countersign`, a second container with its own key): `POST /countersign {dir}` reads the inputs from the shared volume, recomputes, compares roots, totals and digest, fetches the registry's events itself up to `registry_block` and compares them with the inputs', re-reads at that block the names' records (payout addresses), the Settlement accounts and the tier prices and the block's time, recomputes the previous period from the inputs whose hash is on chain and compares the result with `prev.json`, takes the origin digests again, checks the period number against the contract and the contract's own `digest()`, and only then signs.
- Offline modes for anyone with the directory: `recompute DIR` (reproduce and compare, exit 1 on a difference), `report DIR` (the period in plain text), `proof DIR PAYEE` (cumulative amount and Merkle proof for `claim`).
- Devnet: compose profile `settlement` (five `auditor-<city>`, `aggregator`, `countersigner`, volume `settlement-data`) and profile `sabotage` (`auditor-spoof`, `auditor-liar`, `origin-tampered`); `accounts.json` gained `origin`, `asset_list` and `cache_rules` (the tier's price, 7,200 USDC a day, i.e. 10 USDC per two-minute period, is in the on-chain price table); `deploy/scripts/demo-settlement.sh` checks the account the deploy created and funded, starts the loop (the nodes reveal their own token keys), sabotages (Seoul restarted with `origin` pointing at `origin-tampered`, Tokyo stopped, the two bad humans), waits for the first full period after that, prints the report, recomputes on the countersigner, checks the outcome, walks through the claim, the void, the republish and the final claim, then undoes the sabotage and leaves the loop running.

Deviations from the sketch above, on purpose: `reqwest` in place of `wreq` (the browser fingerprint is an M4 hardening item; nothing on the devnet inspects TLS); JSONL files instead of SQLite (the inbox already is the inputs format); no `/v1/asset-samples` endpoint (the aggregator digests the origin itself until the control plane exists; the digests are inputs either way); inputs on a shared volume rather than kubo; the day's seed is `keccak256(day)` (the assignment's) rather than an L1 block hash; the scorer does not check that a probe was on schedule; an attempt at a period number that never published is overwritten by the next attempt. Not built yet: class probes (`/.well-known/dedan/blob/50`), resolver-conformance probes (no `ROLE_RESOLVER_OPERATOR` holder exists on the devnet, so the resolver pool's share goes to the protocol fee), entry audits, and the `anchor` flag on attestations made during assigned probes.

## Aggregator inputs and outputs (the recompute contract)

```
inputs/
  manifest.json           period (the contract's number), wall period and bounds, registry_block, chain id, Settlement and
                          governance (treasury) addresses, price_table_version, score_version, period_secs, sample_n, map_k,
                          auditors_per_account, prev_outputs_hash, files{name: sha256}
  registry-events.jsonl   every decoded DedanRegistry and DedanCells event from block 0 to registry_block, in chain order:
                          roles, names, stakes, suspensions, key reveals, membership, attestations
  probe-results.jsonl     the ProbeBatch envelopes filed in the wall period, sorted by (signer, ts, hash); verified again
                          in compute (signature, role and stake, signed inside the period, each nonce once), rejected ones
                          listed in outputs/rejected-batches.json and counted for nothing
  asset-samples.jsonl     AssetSample per account: the day's sampled assets with sha256 current and previous, size, etag
                          (digested from the origin by the aggregator; signed by the control plane from M3)
  configs.jsonl           the account configs the control plane relays, as envelopes; compute keeps the newest one each
                          account key signed
  accounts.json           every account of the Settlement contract at registry_block: key, balance, applied bill, pending
                          withdrawal (the bill cap and the zero leaves)
  prices.json             the daily price of each tier the configs use, from the on-chain table at registry_block
  nodes.json              the names' records at close: payout, ipv4, port, class, location
  geo.json                prefix -> point (the host tables; a GeoIP database version in production)
  prev.json               the previous period's cumulative leaves, slot sets and member quality
outputs/
  map.json                covered cells, ranked nodes with medians and human counts, node location estimates, anchor
                          disagreements, this period's rejected attestations
  assignment.json         slot sets (sticky on prev.json)
  score.json              core::score's whole output: quality per (account, node), multipliers, payouts, auditor pay,
                          protocol fee, cumulative leaves, class qualification, evidence
  evidence.json           mismatches, invalid tokens, outliers, unmeasured members, spoofed attestations
  payout-leaves.json      (payee, cumulative, proof); bill-leaves.json the same per account
  next.json               prev.json of the next period
  roots.json              RootInput, digest, signatures, publishRoot transaction
```
`inputs_hash = sha256(manifest.json)`. `recompute` reproduces the roots, totals and digest from `inputs/` and compares them with `outputs/roots.json`. Anything not in `inputs/` cannot influence money or the map. The countersigner also re-reads at `registry_block` everything in `inputs/` that comes from the chain (records, accounts, prices, the block's time, the events), recomputes the previous period from the inputs whose hash is on chain to check `prev.json`, and takes the origin digests again.

## Risks to the demo

| Risk | Answer |
|---|---|
| Rust images build slowly | `cargo-chef`, `make images` once, host-side `cargo run` |
| Pingora on macOS | check at M3 start; fall back to the Linux container |
| Period clock vs chain clock | wall-time periods; anvil advanced only for the dispute window |
| `tc` has seven bands per host | per-city bands from the M1 growth |
| k = 1 on the devnet hides collusion cases | the `core::map` fixtures cover them (a node needs k votes of its own to rank); the demo shows the spoofed batch as one vote plus evidence, which does not need k |
| Token keys on a compressed clock | the nodes reveal their own keys; the devnet's governance flag lets them reveal the current hour at once (production reveals only after the hour, once), so tokens verify inside a two-minute period |
| Assignment stickiness state | shared: the resolver and the auditors take the previous period from the aggregator's `/v1/previous` (its published sets, member quality and cumulative bills); before the first period, or without the settlement loop, nobody has one and the sets still agree |
| Attester gas on World Chain | each attester key holds a little ETH on the devnet; a paymaster is an M4 item |
| EAC's 15 holders per role per resource | population roles live on per-human resources; a node hands out at most 15 signer keys |
| `<label>.dedan.eth` is not a canonical `.eth` name yet | the tree mirrors ENS; bridging canonical `dedan.eth` to this registry is a pointer, not a rename |
